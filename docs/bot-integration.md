# Контракт шлюза с Grok Bot

Это единственный документ, по которому настраивается routine бота. Этап 0 не знает точного имени заголовка ключа у webhook бота и лимита размера тела, поэтому исходящая аутентификация настраивается переменными окружения, а не зашита в код.

Шлюз говорит с ботом в две стороны:

1. **Исходящее.** Шлюз делает `POST` на webhook routine, когда телефон поставил команду в очередь.
2. **Входящее.** Бот отвечает отдельным `POST` на шлюз. Тем же вызовом бот присылает события без команды, например сводку в 06:00 МСК.

Телефон результат не получает в ответе на свою команду. Он опрашивает `GET /v1/commands/{id}` или `GET /v1/events`.

## Переменные окружения

| Переменная | Обязательна | Смысл |
|---|---|---|
| `BOT_BRIDGE` | нет, по умолчанию `mock` | `webhook` — реальный бот. `mock` — шлюз сам отвечает и ходит на свой `/v1/bot/results`. |
| `BOT_WEBHOOK_URL` | да, если `webhook` | Полный URL webhook routine. В git не класть. |
| `BOT_WEBHOOK_AUTH_HEADER` | нет, по умолчанию `Authorization` | Имя заголовка ключа отправителя. Поставить то, которое проверяет бот. |
| `BOT_WEBHOOK_AUTH_VALUE` | да, если `webhook` | Значение заголовка целиком, например `Bearer <sender key>`. |
| `BOT_WEBHOOK_TIMEOUT_SECONDS` | нет, `10` | Таймаут одного исходящего POST. |
| `BOT_WEBHOOK_MAX_RETRIES` | нет, `3` | Число попыток. Повтор только при сети и статусе 5xx. 4xx — сразу ошибка. |
| `BOT_WEBHOOK_RETRY_BASE_MILLIS` | нет, `200` | Пауза перед повтором: `base << номер_попытки`. |
| `BOT_INBOUND_SECRET` | да | Общий секрет HMAC. Тот же секрет прописать в routine бота. Не меньше 16 символов. |
| `BOT_INBOUND_MAX_SKEW_SECONDS` | нет, `300` | Допустимый разъезд часов. |
| `GATEWAY_PUBLIC_URL` | нет, `http://127.0.0.1:$PORT` | Внешний origin шлюза без пути. Бот вызывает `{GATEWAY_PUBLIC_URL}/v1/bot/results`. Для боя нужен HTTPS. |
| `GATEWAY_INTERNAL_URL` | нет, `http://127.0.0.1:$PORT` | Куда mock-бот ходит сам на себя. Настоящему боту не нужна. |
| `USER_TIMEZONE` | нет, `Europe/Moscow` | Пишется в строку пользователя. Время в исходящем событии на этапе 0 всё равно МСК. |

Секреты задаются только окружением. В репозитории их нет.

## Исходящее событие: шлюз → бот

`POST {BOT_WEBHOOK_URL}`

Заголовки:

- `Content-Type: application/json`
- `User-Agent: goga-gateway/0.1.0`
- `{BOT_WEBHOOK_AUTH_HEADER}: {BOT_WEBHOOK_AUTH_VALUE}`

Тело, поля в таком виде (компактный JSON, `null` не отправляется):

```json
{
  "event": "command.created",
  "command_id": "11111111-1111-1111-1111-111111111111",
  "text": "напомни позвонить Сергею в пять",
  "timestamp": "2026-10-06T09:59:00+03:00",
  "source": "voice",
  "device_id": "22222222-2222-2222-2222-222222222222",
  "user_id": "33333333-3333-3333-3333-333333333333",
  "callback": {
    "url": "https://gateway.example/v1/bot/results",
    "scheme": "hmac-sha256",
    "timestamp_header": "X-Goga-Timestamp",
    "signature_header": "X-Goga-Signature",
    "signed_payload": "{unix_seconds}.{raw_body}"
  }
}
```

- `timestamp` — момент создания команды, `Europe/Moscow`, точность до секунды, смещение `+03:00`. Пример утренней сводки: `2026-10-06T06:00:00+03:00` это `2026-10-06T03:00:00Z`.
- `source`: `voice`, `text`, `widget`, `notification`, `system`.
- `callback` не содержит секрета. Секрет бот уже знает.
- Успех для шлюза — любой HTTP 2xx. Тело ответа шлюз не читает: результат приходит отдельным вызовом.
- Пока результата нет, команда в статусе `dispatched`. Если webhook так и не ответил 2xx, статус `failed`, телефон видит поле `error` без URL вебхука.

## Входящий результат: бот → шлюз

`POST {GATEWAY_PUBLIC_URL}/v1/bot/results`

Заголовки:

- `Content-Type: application/json; charset=utf-8`
- `X-Goga-Timestamp` — Unix-время в секундах, ровно 10 цифр. Миллисекунды не принимаются.
- `X-Goga-Signature` — hex HMAC-SHA256 в нижнем регистре. Верхний регистр тоже принимается.

Подпись считается от **сырых байтов тела**, которые уходят в сокет:

```text
message = timestamp_ascii + "." + raw_body_bytes
signature = hex(HMAC_SHA256(BOT_INBOUND_SECRET, message))
```

Кодировка тела — UTF-8. Пробелы, порядок ключей и перевод строки входят в подпись. Повтор должен отправить те же байты. Если собрать JSON заново и байты изменятся, для того же `command_id` шлюз ответит `409`.

Часы шлюза и бота должны быть в пределах `BOT_INBOUND_MAX_SKEW_SECONDS` (по умолчанию 5 минут). Имеет смысл NTP.

Проверка:

1. Подпись не сходится → `401`, `error=unauthorized`. Тело не разбирается.
2. Эта подпись уже сохранена → `200` и исходный результат, `idempotent: true`. Так можно повторить запрос даже после окна в 5 минут.
3. Подпись новая, но метка времени вне окна → `401`, `error=expired_timestamp`.
4. Подпись новая и свежая → разбор JSON и запись.

Лимит тела — 100 КиБ. Больше → `413`.

### Ответ на команду

```json
{
  "command_id": "11111111-1111-1111-1111-111111111111",
  "kind": "reply",
  "reply_text": "Записал заметку «сравнение тарифов хостинга».",
  "entities": [
    {
      "type": "note",
      "title": "Хостинг",
      "body": "сравнение тарифов хостинга"
    }
  ]
}
```

`kind`:

| kind | Что обязательно |
|---|---|
| `reply` | непустой `reply_text` — это текст, который телефон потом произнесёт |
| `clarification` | непустой `question` |
| `event` | `reply_text` или непустой `entities` |

`command_id` должен быть UUID команды, которую шлюз уже принял. Неизвестный id → `404`.

### Событие без команды

Утренняя сводка и напоминание, созданное на стороне бота. `command_id` нет, `event_id` обязателен (UUID, его выбирает бот):

```json
{
  "event_id": "44444444-4444-4444-4444-444444444444",
  "kind": "event",
  "reply_text": "Сводка на сегодня: стендап в 10:00."
}
```

Телефон забирает такие события через `GET /v1/events` с токеном устройства. Туда попадают только записи без `command_id`. Если задать `device_id`, событие увидит только это устройство; без `device_id` его видят все устройства пользователя.

### Сущности

`entities[].type`: `note`, `task`, `reminder`, `calendar_event`.

На этапе 0 в базу как запись попадает только `note` (`title` или `body` обязательны, пустой заголовок становится «Заметка»). `id` можно не передавать — шлюз выдаст UUID. Если передать свой UUID и такая заметка уже есть, вторая не создаётся.

`task`, `reminder` и `calendar_event` сохраняются в JSON результата как есть. Отдельных таблиц под них ещё нет. Дополнительные поля календаря класть в `payload` (произвольный объект).

Ответ шлюза:

```json
{
  "result_id": "55555555-5555-5555-5555-555555555555",
  "command_id": "11111111-1111-1111-1111-111111111111",
  "event_id": null,
  "status": "completed",
  "created_note_ids": ["66666666-6666-6666-6666-666666666666"],
  "idempotent": false
}
```

Для события без команды `status` равен `accepted`.

Идемпотентность:

- тот же `command_id` или `event_id` и тот же SHA-256 тела → `200`, `idempotent: true`, заметки второй раз не создаются;
- тот же id и другие байты → `409`, `error=conflict`.

Неизвестный `kind` или `type` → `400`.

## Пример curl

Секрет и тело ниже — проверочный вектор. Подпись для них фиксирована, тест в репозитории её проверяет.

```bash
export BOT_INBOUND_SECRET=test-inbound-secret
export GATEWAY_URL=http://127.0.0.1:8080
export GOGA_TIMESTAMP=1760000000
BODY='{"command_id":"11111111-1111-1111-1111-111111111111","kind":"reply","reply_text":"Готово"}'

# ожидаемая подпись:
# 70f325c871ec736ddbc7ae1ba5f38023a09fbf2486208bce5077ac3934a3d185

bash server/scripts/post-bot-result.sh "$BODY"
```

Тот же расчёт вручную:

```bash
SIG=$(printf '%s' "${GOGA_TIMESTAMP}.${BODY}" \
  | openssl dgst -sha256 -hmac "$BOT_INBOUND_SECRET" -hex | awk '{print $NF}')

curl --fail-with-body -sS -X POST "$GATEWAY_URL/v1/bot/results" \
  -H "Content-Type: application/json; charset=utf-8" \
  -H "X-Goga-Timestamp: $GOGA_TIMESTAMP" \
  -H "X-Goga-Signature: $SIG" \
  --data-binary "$BODY"
```

Для файла с точными байтами: `bash server/scripts/post-bot-result.sh --file body.json`.

Скрипт не добавляет перевод строки к телу. `printf` и `--data-binary` отправляют те же байты, которые вошли в HMAC.

## Что делает телефон

Это не вызовы бота, но без них нечего отвечать.

1. Кто-то с `GATEWAY_BOOTSTRAP_TOKEN` делает `POST /v1/pairing-codes` и получает одноразовый код на 10 минут (`PAIRING_CODE_TTL_SECONDS`). Бот тоже может выписать код, если ему дали этот токен: `Authorization: Bearer <GATEWAY_BOOTSTRAP_TOKEN>`.
2. Телефон: `POST /v1/devices/pair` с кодом и именем устройства. В ответ один раз приходит `device_token`. В базе лежит только SHA-256.
3. `POST /v1/commands` с `Authorization: Bearer <device_token>`:

```json
{
  "idempotency_key": "77777777-7777-7777-7777-777777777777",
  "text": "заметка: сравнить тарифы хостинга",
  "source": "text"
}
```

Новая команда → `202` и статус `queued`. Повтор того же ключа и того же текста → `200` и та же команда. Тот же ключ и другой текст → `409`.

4. Шлюз забирает `queued`, ставит `dispatched` и вызывает бота.
5. Телефон опрашивает `GET /v1/commands/{id}`, пока статус не станет `completed` или `failed`.

`MockBotBridge` (`BOT_BRIDGE=mock`) после исходящего события сам подписывает ответ «Принято: {текст}» и создаёт заметку с этим текстом. Так проверяется весь круг без настоящего бота. Интеграционный тест это делает.

## Повтор и таймауты

- Шлюз повторяет webhook до `BOT_WEBHOOK_MAX_RETRIES` раз. Routine должна спокойно принять один и тот же `command_id` дважды и один раз вызвать шлюз (или вызвать дважды теми же байтами).
- Бот повторяет `POST /v1/bot/results` при сети, `401 expired_timestamp` (с новой меткой времени и теми же байтами) и `5xx`. При `409` байты расходятся с уже записанным результатом — это ошибка routine, а не повод слать третий вариант.
- Ответ бота может прийти через секунды. Шлюз не обрывает команду по таймеру ожидания результата: она остаётся `dispatched`, пока не придёт результат или пока доставка webhook не будет признана неудачной.
